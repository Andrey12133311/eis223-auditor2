# Сохранение свежих доказательств и полнота вывода по критерию

Основа: `8526349`, продолжение PR №112. Рабочие данные и решения сотрудников
не используются как тестовые; воспроизведения выполняются во временных базах.

## Воспроизведённые проблемы

1. Старое ограничение `UNIQUE(batch_id,reg,category,title,evidence)` не учитывает
   документ, URL, код и норму. Новый проверенный источник с той же цитатой
   пропускался при сохранении. Журнал подтверждал новое доказательство,
   которого не было в результатах, а старое правильно оставлял на проверке:
   вместо одного текущего подтверждения получался ноль.
2. Узкое зарегистрированное правило вместе с флагом `criterion_complete=True`
   могло поставить «Нет нарушения» всему пункту листа. Реальных эмиттеров этого
   флага в действующем анализаторе не найдено: исправляется опасный контракт
   входа квалификатора, а не заявленная ошибка конкретной рабочей закупки.
3. Точный ключ перепроверки учитывал код, цитату, документ и URL, но не норму.
   Свежий вывод с исправленным правовым основанием мог подтвердить прежнюю
   строку с другой или отсутствующей нормой. Сохранённая квалификация должна
   подтверждаться вместе с её основанием.

## Реализация

Дополнительный реестр вариантов доказательств сохраняет новую точную
репрезентацию рядом с исторической таблицей. Сохраняются прежние строки,
rowid, ключи выводов, обращения сотрудников и решения руководителей.
Доказательства с разными материальными реквизитами получают собственные ключи;
решение по прежнему источнику не переносится на новое обвинение.

Публичная идентичность включает закупку, заголовок, норму, цитату, документ
и точный URL. Внутренний код анализатора не меняет этот ключ. Для совершенно
одинакового материального обвинения актуальное явное подтверждение имеет
приоритет над старой внутренней меткой; явная необходимость проверки имеет
приоритет над неподтверждённым legacy-значением по умолчанию. Исходные строки
обоих анализаторов сохраняются. Разные нормы, цитаты и источники остаются
разными публичными доказательствами.

Общие читатели используют объединённый набор исходных доказательств. Обе
оценки актуальности применяются до объединения представлений одного эпизода.
Отдельный поиск по точному ключу позволяет открыть ранее отправленный на
рассмотрение источник даже при выборе другого представителя в общей карточке.
Пользовательские счётчики продолжают считать самостоятельные юридические
эпизоды. Повтор того же доказательства не создаёт новых записей.

Инициализация дополнительной таблицы выполняется при подготовке схемы.
Чтение старой базы без новой таблицы сохраняет прежний путь и не выполняет DDL.
Запись нового доказательства, журнала и состояния попытки остаётся атомарной;
проверки владельца, периода, кампании и текущего резервирования сохраняются.
Явное удаление тематической проверки охватывает дополнительный реестр,
остановка обработки сохраняет историю.

Отметка о полном соблюдении требует явно зарегистрированного полного
валидатора критерия. Сейчас таких валидаторов нет. Узкие правила продолжают
подтверждать установленные нарушения и вопросы для проверки; служебный флаг
не превращает их в полное заключение по пункту. Ручные решения руководителя
относятся к отдельному процессу и сохраняются.

Ключ перепроверки включает точную строку нормы. Изменение правового основания
требует отдельной свежей квалификации. Заголовок и URL справочной страницы
сохраняют роль представления; публичный ключ исходного решения не меняется.
Новая редакция журнала перепроверки оставляет старые записи историей.

## План проверки

- [x] Свежий источник B сохраняется при старом A с той же цитатой; A остаётся
  историей, B подтверждается, прежнее решение A не утверждает B.
- [x] Повтор B идемпотентен; две текущие копии одного эпизода дают один
  пользовательский счётчик; самостоятельные эпизоды сохраняются отдельно.
- [x] Точный источник ранее отправленного вывода открывается независимо от
  выбора представителя; оба журнала актуальности применяются до объединения.
- [x] Сбой, конкурирующая запись или потеря резервирования не оставляют
  частично сохранённого подтверждения; чтение и сравнение выполняются вне writer.
- [x] Старые read-only базы, кэши, выгрузки, кабинеты, удаление и существующий
  журнал уведомлений учитывают новый реестр с прежними границами доступа.
- [x] Узкое правило не подтверждает полное соблюдение критерия через флаг;
  API, обе формы листа и общий/тематический пути сохраняют незавершённость.
- [x] Другая или отсутствующая норма не подтверждается свежим выводом по
  совпадающей цитате; история и решения остаются неизменны.
- [x] Независимое ревью, необходимые Docker-проверки и полный набор unittest.

Добавлено 67 регрессий в шести модулях. Их заключительный прогон вместе
с двумя проверками регистрации юридического конвейера: 69 тестов за 5,954 с,
`OK`. Независимые проверки сохранения и читателей завершены; дополнительно
проверено ограниченное окно кабинета сотрудника при 1 250 исторических
записях каждого типа. Два курсора выбирают не более 1 200 строк суммарно,
пополняя выборку из оставшегося потока при исчерпании второго. Порядок
сохраняется и в ограниченном показе 500 карточек. Фильтры владельца, выбранных
категорий и участия закупки применяются до ограничения.

Четыре прежних положительных ожидания узкой проверки заменены проверкой
недостаточности полного заключения; тесты согласованности статусов и области
применения сохранены. Ожидания ключа источника теперь читают и сравнивают
реально сохранённую норму. Прежняя staff-фикстура не требует одновременно
двух статусов одного точного публичного обвинения: исторический источник
отдельно проверяется в своей тематической проверке вместе с прежним решением.

Фикстура smoke-тестов кабинета ждёт свои фоновые чтения после startup и перед
удалением временной базы. Это устраняет гонку незавершённого prewarm с
проверкой HTTP-результата и очисткой каталога; ожидание относится к реальному
Future, без пауз, повторов запросов и подавления ошибок. Пять исходных
маршрутных проверок сохранены. Управляемая задержка фонового чтения отдельно
подтвердила, что очистка начинается после его завершения.

В существующем golden-образе проверены 374 разных unittest без пропусков
и все 39 запусков legacy selftests. Проверка выполнена тремя offline-контейнерами:
первый прошёл 346 тестов и первые 35 selftests, затем остановился на
устаревшем сравнении буквальной SQL-строки в selftest кабинета сотрудника.
Проверка заменена утверждениями о действующих фильтрах доступа и лимитах;
повторно прошли selftests № 36–39. Третий запуск проверил 23 теста юридической
квалификации и пять smoke-тестов кабинета после исправления их фикстур.
Пересечения с первыми 346 тестами нет. Между снимками изменились только
указанный selftest и два файла тестов; production-код совпал. Все 491 Python-файл
сверены по SHA-256 до и после запусков и с заключительным рабочим набором.
Каталоги исходников подключены read-only, сеть отключена. Новая полная
Docker-сборка не выполнялась; Dockerfile включает шесть новых модулей.

Заключительный полный прогон после исправления фикстур: 2 849 тестов за
298,009 с, `OK (skipped=7)`. Все 67 новых регрессий выполнены. После прогона
повторно сверены 491 Python-файл и Dockerfile с финальным Docker-снимком;
исходники не изменились. Начальный полный прогон и диагностические
воспроизведения сохранены отдельно от заключительного результата.

Публикация нового кода по-прежнему зависит от активации тарифа Railway.
